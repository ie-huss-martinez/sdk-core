# 0016. Tabs that are sections first, and one component

- **Status:** Accepted
- **Date:** 2026-11-26
- **Builds on:** [ADR 0003](0003-component-contract.md), the component contract, and [ADR 0015](0015-tag-and-button-link.md), which brought `ui` to static pages

## Context

Fish Memory's explainers show the same idea in several stacks, one at a time: "In your stack", with a tab for each. It's a static Astro site. Today it renders every implementation in full, with a hidden tab list, and a small script turns that into tabs when it runs. The script and its markup are the site's own, and so are their keyboard and screen-reader behaviour.

`ui` has a `TabBar`, which is the row of tools at the foot of a phone's editor: a toolbar of buttons, not tabs with panels. It has nothing for the [WAI-ARIA tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/).

Three things shape a tabs component for these pages:

- **The page must be complete without JavaScript.** A static page that never hydrates a component still has to show its content, and a page that will hydrate has to make sense until it does. Tabs that render one panel and hide the rest fail both: the hidden panels can't be reached.
- **A role is a promise.** An element announced as a tab promises the arrow keys. Before any script runs, nothing keeps it.
- **Astro renders each React component on its own** ([ADR 0015](0015-tag-and-button-link.md)). Components written side by side in an `.astro` file share no React context, and only one that is hydrated as a whole, an island, gets its handlers. A tab list, its tabs and their panels as separate components couldn't find each other there.

## Decision

### One component, given its tabs as data

- **`Tabs` takes `tabs`, a list of `{ id, label, icon, content }`,** and `label`, the row's accessible name, which is required. There is no `TabList`, `Tab` or `TabPanel` to compose, and no context between parts: the ids that tie a tab to its panel, the selection and the keys are all inside one component, so it's one island.
- **`label` on each tab is text.** It's the tab's name and, before the tabs are ready, the heading over its panel. `icon` is decorative.
- **Selection** is `defaultValue` for a component that keeps it, or `value` with `onValueChange` for an owner that does. An id that names no tab selects the first.

### Sections first, then tabs

- **On the server, and while hydrating, it renders every panel,** one after another, each under a heading with its tab's label. No tab list, no roles, nothing hidden and nothing focusable: a set of titled sections, which is what it is until it can be operated.
- **The headings' level comes from the host,** as everywhere in the family ([ADR 0058 of the family](../../../../docs/adr/0058-heading-levels-in-editors.md)): `headingLevel`, or the closest `HeadingLevelProvider`'s, or 2. A panel's own `Heading`s are one level below its title while the title is there, and never past 6. Once the tabs are ready the title is gone, and a tab isn't a heading, so they take the title's level, and no level is skipped.
- **Once it runs in a browser, it becomes tabs.** Whether it's ready comes from `useSyncExternalStore` with a server snapshot of `false`, as `usePlatform`'s platform does, so the server's markup and hydration agree, and no effect sets state. Rendered in a browser from the start, it's tabs at once.
- **What's inside a panel survives the change.** Each panel is the same element before and after, with its content in the same place among its children; only its role, its name and its heading change. A panel's own state, and its DOM, aren't made again.
- **The cost is one shift of layout,** when the sections collapse to one panel. A page that hydrates its tabs early, before they're in view, doesn't show it.

### The tabs pattern, as the Authoring Practices describe it

- **Roles:** `tablist` named by `label`, `tab` with `aria-selected` and `aria-controls`, and `tabpanel` named by its tab.
- **One Tab stop for the row,** on the selected tab. → and ← move between tabs, wrapping, and swap in right-to-left text, where the row runs the other way; Home and End go to the first and the last.
- **`activation`** is `automatic` by default: the arrow keys select as they move, which is right when a panel is already there. `manual` only moves focus, and Enter or Space select, for panels that are slow to show.
- **Every panel stays in the document,** the others with `hidden`. A panel keeps its state while another shows, and nothing is fetched or rendered on selection.
- **The panel is a Tab stop,** so a panel of plain text can be reached, read and scrolled from the keyboard. With focusable content inside, it's one stop more than strictly needed; that's the price of one rule that's always right.
- **A row too long for its width scrolls sideways,** and keeps its selected tab in view: at first, when its owner changes the selection, and when the row gets its size, which it has none of inside a closed dialog or another tab's hidden panel. A `ResizeObserver` on the row does all three. Only the row is scrolled, never the page. The row itself is taken out of the Tab order, because Firefox makes a scrolling element a stop of its own, before its tabs.
- **The selected tab is marked by a line under it,** as well as by its colour (WCAG 1.4.1). Only the selected tab has that border; the others hold its place with padding, so selecting moves nothing. A transparent border on every tab would do the same on screen, and forced-colours mode, which draws every border, would then underline them all.
- **Each visual rule reaches its part through its own root,** child by child, so tabs inside another's panel keep their own `unstyled`.

### Not in this version

Vertical tabs, disabled tabs, tabs that close, and a tab's own address in the page's URL. None is needed yet, and each is a decision about keys or history that deserves its own.

## Alternatives considered

- **A compound API,** `<Tabs><TabList><Tab>…</Tab></TabList><TabPanel>…</TabPanel></Tabs>`: it lets a caller put anything in a tab and anywhere around the list. It needs context between parts, which Astro's pages don't have, it leaves the pairing of tabs and panels to the caller, and its static form is the caller's problem. `ui`'s `SegmentedControl`, `TabBar` and `ToolList` take their items as data for the same reasons.
- **Tabs from the first byte, with the selected panel only:** no shift of layout. The other panels are unreachable without JavaScript, and the roles promise keys that don't work until it loads.
- **Tabs without JavaScript, from radio inputs or `<details name>` in CSS:** they switch without script. Radios styled as tabs are announced as radio buttons, and exclusive `<details>` as disclosures, so neither is the tabs pattern, and switching between the two models at hydration would change what a screen reader says mid-page.
- **Setting a "mounted" state in an effect:** the usual way to render differently after hydration. It's a state set in an effect, which the family's React lint refuses ([ADR 0063 of the family](../../../../docs/adr/0063-a-lint-for-what-react-components-do-while-rendering.md)), and it renders the static form once even in a page that never had it.
- **Rendering only the selected panel,** and the others on demand: lighter pages. It loses a panel's state on every switch, and `content` is already rendered by the caller, so nothing would be saved here.
- **`tabindex="0"` on the panel only when it has nothing focusable inside:** one stop fewer in some panels. It needs the DOM read after every render, and it changes under the user as content does.
- **`scrollIntoView` for the selected tab:** one call. It also scrolls the page to the row, so tabs below the fold would move the page when they hydrate.

## Consequences

- A page gets tabs whose keyboard and screen-reader behaviour is tested once: unit tests of the server markup, browser tests on three engines for the keys, focus, hydration and scrolling, and a virtual screen-reader test of what's heard.
- **One export and eleven component tokens,** `--hm-tabs-*`. It ships `Heading` with it, for the static form.
- **Callers can't put arbitrary markup in a tab,** such as two lines of text. A label and an icon cover what's needed; `classNames` and the tokens restyle them.
- **A static page that never hydrates `Tabs` gets sections, not tabs.** That's by design, and the README says how to hydrate it in Astro.
- **The layout shifts once at hydration,** as above.
- **Printing shows the selected panel only,** like any hidden content. Showing every panel in print would be a small follow-up.
